#### D-25 — 사원 레코드 생성: A안(자율 등록) ✅ 확정

```
이름 + 전화번호 입력

async function resolveEmployee(name: string, phone: string) {

```

|---|---|
| 사내 공용 접근 코드 (예: `1289123`) | 회사 전체가 공유하는 값이라 **동료 사칭을 전혀 못 막습니다.** 막아주는 건 "회사 코드를 모르는 완전 외부인"뿐인데, 사내 서버 배포(D-04)라 외부인이 로그인 화면에 닿기 어렵습니다. 얻는 것에 비해 매 로그인마다 한 개를 더 입력해야 하는 부담이 큼 |
| 개인 PIN 4자리 | 동료 사칭을 실제로 막을 수 있는 유일한 안이었으나, **"이름+전화번호만으로 간다"는 단순함을 우선**하기로 결정. 최초 로그인 시 PIN 설정 단계가 늘어나는 것도 부담 |

> ⚠️ **그래서 남는 한계**: 동료의 이름과 전화번호를 아는 사람이 그 사람인 척 로그인해 결과를 볼 수 있습니다. 사내에서 이름·전화번호는 원래 비밀이 아니므로 이건 **구조적으로 열려 있는 상태**입니다. 이 사실을 §5 리스크표에 명시적으로 기록해 두고, 나중에 필요해지면 `AuthProvider` 교체(사번+비밀번호, SSO)로 해결합니다 — 그때 고쳐야 할 파일은 `lib/auth/` 안뿐입니다.

#### 로그인 실패 제한 — 최소 구현 (✅ 확정, 널널하게)

이름+전화번호가 인증이 아니라는 한계는 위에서 본 대로 남아 있습니다. 이름을 아는 사람이 전화번호를 스크립트로 반복 시도할 가능성에 대해, 구현 비용이 거의 없는 완화책 하나만 추가합니다.

| 항목 | 값 |
|---|---|
| 기준 | **(이름, 전화번호) 조합** 단위 — IP 기준 아님 |
| 임계값 | **5분 내 10회 실패** (관리자는 5회) |
| 잠금 시간 | **5분**, 자동 해제 (관리자 개입 불필요) |
| 저장 위치 | **인메모리(Map)** — DB 스키마 변경 없음. 서버가 하나뿐인 배포(D-04)라 재시작으로 초기화돼도 문제없음 |

**IP가 아니라 (이름, 전화번호) 조합으로 제한하는 이유**: 사내 여러 사원이 같은 공인 IP(사무실 네트워크)를 씁니다. IP 단위로 막으면 한 사람이 여러 번 틀렸다고 사무실 전체가 로그인을 못 하게 됩니다. 특정 조합만 잠그면 그 문제가 없습니다.

**여전히 남는 한계**: 공격자가 여러 이름을 돌아가며 시도하면(이름마다 몇 번씩만) 이 제한을 피해갈 수 있습니다. 완벽한 방어가 아니라 "스크립트로 한 사람의 번호를 반복 시도"하는 가장 흔한 패턴만 막는 최소 조치입니다. 애초에 동료 사칭은 이 제한으로 막을 수 없습니다 — 동료는 번호를 이미 알고 있어 한 번에 맞히기 때문입니다(위 D-27 절 참조).

### 동의 기록 — 이미 있음, 새로 안 만듦 (D-14 관련)

"동의했다"는 증빙이 나중에 필요할 수 있어 별도 체크박스·타임스탬프 필드를 만들자고 제안했으나, **다시 보니 이미 있는 데이터로 충분합니다.**

`TestSession.startedAt`은 사원이 시작 화면(고지문, `01` §2.9)을 보고 "검사 시작하기"를 눌러야만 생성됩니다. **이 값 자체가 곧 "이 시점에 고지문을 보고 진행했다"는 기록**입니다. 새 필드·체크박스·새 화면 전부 필요 없습니다.

**유일하게 진짜 빠지는 것**: 고지문 문구가 나중에 바뀌면 "어느 버전을 보고 동의했는지"가 안 남습니다. 지금은 문구를 바꿀 계획이 없어 실제로 발생할 가능성이 낮은 문제입니다. 나중에 문구를 바꿀 일이 생기면 그때 컬럼 하나(`policyVersion`) 추가하면 됩니다 — 지금 만들지 않습니다.

### 💡 2.2 큐브 해석 모델 — 해설 자동 생성의 학술적 근거

기술검토서 §12가 "가장 유용"하다고 표시한 2014년 논문(이수진·Cloninger·채한)의 실제 내용을 확인했습니다. **기질 3축과 성격 3축을 각각 고/저로 나눠 2³=8유형 큐브를 만드는 방식**입니다.

```
기질 큐브 : NS × HA × RD   (PS는 큐브에 안 들어감)
성격 큐브 : SD × CO × ST

표기법: 대문자 = 높음, 소문자 = 낮음
  NhR = NS↑ HA↓ RD↑   → 논문 표현 "열정적"
  nhr = NS↓ HA↓ RD↓   → "독립적"
  NHr = NS↑ HA↑ RD↓   → "폭발적"
  SCT = SD↑ CO↑ ST↑   → "창의적"
  sct = SD↓ CO↓ ST↓   → "무관심"
```

**이게 왜 중요하냐면** — 기술검토서 F-17("척도 조합 자동 해설")이 "어떻게 만들지" 없이 아이디어로만 있었는데, 이 큐브가 **그 규칙 테이블의 실제 골격**입니다. 근거 있는 자료 기반이라는 요구도 충족합니다.

> ### ❌ 2026-08-23 — 큐브를 쓰지 않기로 했습니다
>
> 실제로 만들어 넣어본 뒤 확인한 결과입니다.
>
> **하나, 논문의 8유형 서술은 임상 용어입니다.** NHr = "Borderline / Explosive — 미성숙, 정서 불안정", sct = "Apathetic", sCT = "Moody". 라벨만 떼고 내용을 옮겨도 "정서가 불안정한 편"이 됩니다. 사내 검사에 쓸 수 없습니다.
>
> **둘, 그래서 서술을 새로 쓰면 논문과의 연결이 끊깁니다.** 남는 것은 "세 축을 묶는다"는 구조뿐이고, 문장은 근거 없는 추론이 됩니다. 근거 있는 척하는 것은 이 프로젝트가 계속 피해온 것입니다.
>
> **셋, 실무 해석은 8칸이 아니라 두 축의 맞물림입니다.** "자극추구가 높아도 위험회피가 함께 높으면 가고 싶지만 두렵다는 내적 긴장"처럼 읽습니다.

>
> ⚠️ **정정 (총량 확정)**: 초안에서는 기질 큐브(8유형)와 성격 큐브(8유형)를 **서로 곱해 8×8=64칸짜리 하나의 매트릭스**로 만든다고 적었으나, 이는 원 논문에 없는 확장이었습니다. **2014년 논문은 두 큐브를 서로 곱하지 않고, 기질 프로파일과 성격 프로파일을 각각 독립적으로 8유형씩** 씁니다. → **기질 8개 + 성격 8개 = 16개**로 정정합니다. 채점 결과가 나오면 기질 큐브에서 하나, 성격 큐브에서 하나, 두 서술을 각각 조회해 나란히 보여줍니다(서로 곱한 하나의 조합 서술이 아님).

### 💡 2.3 불성실 응답 탐지 — 기술검토서의 방법이 틀렸습니다

기술검토서 §3.4는 "**동일 응답 연속 N개 이상**"으로 불성실 응답을 잡자고 되어 있는데, 이건 longstring 지표입니다. **최근 연구에서 longstring과 IRV(개인내 응답 변산)는 탐지력이 없는 것으로 나왔습니다.** 효과 있는 것으로 확인된 건 다음입니다.

| 지표 | 내용 | 우리 구현 난이도 |
|---|---|---|
| **문항별 응답시간** | 문항당 소요시간이 하한 미달이면 플래그 | 쉬움 — 프론트에서 타임스탬프 기록 |
| **Psychometric antonyms** | 반대여야 정상인 문항쌍(정문항/역문항)이 같은 방향인지 | **쉬움 — 역채점 문항이 이미 있음** |
| Psychometric synonyms | 상관이 높아야 정상인 문항쌍의 응답이 어긋나는지 | 중간 — 문항쌍 사전 정의 필요 |
| Mahalanobis 거리 | 다변량 이상치 탐지 | 어려움 — 표본 50명이면 불안정 |
| ~~longstring~~ | ~~동일응답 연속~~ | **효과 없음 → 제외** |

→ **채택: 문항별 응답시간 + psychometric antonyms(역채점 쌍 일치도).** 둘 다 구현이 쉽고 50명 이내 규모에서도 작동합니다. Mahalanobis는 표본이 작아 제외.

### 💡 2.4 문항 뱅크를 앱 코드에서 분리 — 오픈소스 사례 패턴

Next.js로 만들어진 대표적 성격검사 오픈소스 `bigfive-web`(★937)이 **문항 데이터를 웹앱과 별도 패키지로 분리**해두고, 웹앱은 그걸 소비만 합니다. 기술검토서 §5.3의 "문항을 DB에 저장"보다 한 단계 더 나간 구조입니다.

```
data/items/            ← 문항 원본 (사람이 읽고 고치는 파일)
  ns.yaml
  ha.yaml
  ...
  sources.yaml         ← 근거 출처 대응표
      ↓ seed 스크립트
PostgreSQL items 테이블 ← 앱이 읽는 곳
```

**장점**: 문항 초안을 제가 작성하고 → 파일에서 직접 읽고 고치고 → seed 한 번 돌리면 반영. DB 툴을 열 필요가 없고, 파일이라 변경 이력이 남습니다. 기술검토서 F-14(문항 관리 화면)를 P3까지 미뤄도 되는 이유이기도 합니다.

### 💡 2.5 문항 상태 워크플로 — 버전 번호만으로는 부족

기술검토서 §5.2는 `assessments.version` 정수 하나로 개정을 관리합니다. 상용 문항뱅크 플랫폼들은 **문항 단위 상태**를 따로 둡니다.

```
draft → review → active → retired
```

우리에게 필요한 이유: 파일럿에서 부적합 문항을 교체할 때, 문항을 **지우면 과거 응답이 고아가 됩니다.** `retired`로 표시하고 남겨둬야 과거 세션 결과를 다시 계산할 수 있습니다.

### 💡 2.6 결과 스냅샷 — "내 점수가 왜 바뀌었지?" 방지

이건 기술검토서에 없는데, 안 하면 반드시 사고가 납니다.

사내 상대위치는 응시자가 늘 때마다 재계산됩니다. 그러면 **어제 본인 결과를 본 사원이 오늘 다시 들어오면 숫자가 달라져 있습니다.** 자체 제작 검사의 신뢰도를 스스로 깎아먹는 상황입니다.

→ **사원에게 보여준 결과는 스냅샷으로 고정**하고, 재계산은 관리자 분석 화면에서만 최신값을 씁니다. 사원 화면에 "이 결과는 YYYY-MM-DD 기준입니다" 표기.

> **스냅샷 대상은 점수·구간(`band`)까지만. 해설 문구는 대상이 아닙니다.**
> 검토 중 "해설 문구도 스냅샷에 같이 저장해야 하지 않나"라는 질문이 나왔으나, **기각했습니다.** 상대위치를 고정한 이유는 "본인은 안 바뀌었는데 다른 사람 데이터 때문에 숫자가 흔들린다"는 문제였습니다. 해설 문구는 이 문제가 없습니다 — 문구가 바뀌는 유일한 이유는 우리가 글을 고쳐서(오타 수정, 표현 개선)이고, 그건 전원에게 개선된 버전이 적용되는 게 맞습니다. **구간(`band`)은 채점 시점에 이미 고정되므로 "무엇을 보여줄지"는 안 바뀝니다. "어떻게 표현할지"만 항상 최신 문구를 씁니다.**

> ✅ **정정 — 상대위치는 개인 화면에 아예 안 넣기로 확정 (D-09)**
> 초안 검토 중 "스냅샷 고정"과 "상대위치는 30명부터 표시"가 합쳐지면, 30명 근처에서 결과를 먼저 본 사람과 나중에 본 사람이 영구적으로 다른 화면을 보게 되는 문제가 발견됐습니다. 해결책은 **상대위치를 개인 화면에서 아예 빼는 것**입니다 — 개인은 원점수/만점대비%만 보고(이건 시간이 지나도 안 변하므로 스냅샷과 자연히 맞음), 상대위치는 관리자 분석 화면(`01` §4.4)에서만 씁니다. 상세는 D-24(§1), `01` §3.1·§4.4.

### 💡 2.7 채점 엔진을 순수 함수로 격리 + 골든 테스트

기술검토서 §18.2가 "채점 로직 단위 테스트는 꼭 필요"라고 했는데, 구조까지는 안 정했습니다.

### 2.9 ST 처리 — ✅ 확정 (D-21, 안 B′)

**✅ 결정: ST 유지. 현행 TCI-R/TCI-RS의 3-facet 구조(ST1/ST2/ST3)로 구성. ST4·ST5는 삭제.**

초안에서는 "ST가 7척도 중 가장 약하다"고 판단했으나, **TCI 원전 쪽 자료를 추가 조사한 결과 이 판단이 틀렸습니다.** 아래는 정정된 근거입니다.

#### 2.9.1 ST는 원래 검사에서 가장 튼튼한 척도다

Farmer & Goldberg (2008), *Psychological Assessment* — TCI-R / TCI-140을 미국 성인 727명으로 평가. (Goldberg는 IPIP 개발자로, 자료가 공개돼 있음)

**영역별 신뢰도**

| 영역 | TCI-R 전체 | TCI-140 단축형 |
|---|---|---|
| PS 인내력 | .92 | .89 |
| **ST 자기초월** | **.90** | **.89** |
| SD 자율성 | .90 | .88 |
| C 연대감 | .89 | .84 |
| RD 사회적민감성 | .89 | .85 |

ST는 7영역 중 2위입니다. 하위척도 단위로 보면 **ST3 영성수용의 α = `.90`으로 전체 하위척도 중 1위**입니다.

**요인구조는 더 결정적입니다.** 같은 논문이 TCI-R 구조를 꽤 혹독하게 비판하는데 —

| 문제 | 내용 |
|---|---|
| HA ↔ SD | **구분되지 않음** — 양쪽 facet 4개씩이 같은 요인을 형성 |
| C ↔ RD | 잘 분화되지 않음. RD1은 C 요인에 더 높게 적재 |
| SD4 | 여러 요인에 교차 적재 |
| **ST** | **깨끗하게 자기 요인으로 적재** (.89 / .83 / .72) |

→ **ST는 이 검사에서 가장 잘 정의된 축입니다.** 약한 것은 ST 자체가 아니라 **IPIP의 프록시 커버리지**였습니다.

#### 2.9.2 ST4·ST5는 현행 모델에 존재하지 않는다

**현행 TCI-R / 한국판 TCI-RS의 ST 하위척도는 3개뿐입니다.**

| | 문항 수 | α |
|---|---|---|
| ST1 창조적 자기망각 | 10 | .79 |
| ST2 초월적 동일시 | 8 | .77 |
| ST3 영성 수용 | 8 | **.90** |

§2.1의 IPIP 대응표에 있는 **ST4(Conservatism), ST5(Femininity)는 1993년 구버전 TCI 기준**이며, 개정 과정에서 사라진 facet입니다.

→ 이전 초안의 "Femininity를 VIA로 교체하자"는 **프레임 자체가 틀렸습니다.** 교체할 대상이 아니라 **애초에 쓰지 않아야 할 항목**입니다.

#### 2.9.3 한국판 TCI-RS 하위척도 공식 명칭 — 문항 작성의 직접 근거

이숙희·황순택, 「기질 및 성격검사-성인용(TCI-RS)의 구인타당도」, 한국심리학회지: 임상 28(2). **오픈액세스**, 대학생 753명, 전체 α `.85`.

| 척도 | 하위척도 (한국판 공식 명칭, 양극 표기) |
|---|---|
| **NS** | 탐색적 흥분/관습적 안정성 · 충동성/심사숙고 · 무절제/절제 · 자유분방/질서정연 |
| **HA** | 예기불안 · 불확실성에 대한 두려움 · 낯선 사람에 대한 수줍음 · 쉽게 지침 |
| **RD** | 정서적 감수성 · 정서적 개방성 · 친밀감/거리두기 · 의존/독립 |
| **PS** | 근면 · 끈기 · 성취에 대한 야망 · 완벽주의 |
| **SD** | 책임감/책임전가 · 목적의식 · 유능감/무능감 · 자기수용/자기불만 · 자기일치 |
| **CO** | 타인수용 · 공감/둔감 · 이타성/이기성 · 관대함/복수심 · 공평/편파 |
| **ST** | 창조적 자기망각/자의식 · 우주만물과의 일체감 · 영성 수용/합리적 유물론 |

> 💡 **양극 명칭이 역채점 문항 설계를 그대로 알려줍니다.** `영성 수용 / 합리적 유물론`처럼 반대편이 명시돼 있으면 역채점 문항을 어느 방향으로 쓸지가 바로 나옵니다. `합리적 유물론` 쪽 진술이 곧 역채점 문항입니다. 전 척도에 동일하게 적용합니다.

#### 2.9.4 확정된 ST 구성 (안 B′)

```
ST1 창조적 자기망각/자의식   ← TCI-RS facet 정의 + IPIP Imagination(.65) 참고
ST2 우주만물과의 일체감      ← TCI-RS facet 정의 + IPIP Romanticism(.58) 참고
ST3 영성 수용/합리적 유물론   ← TCI-RS facet 정의로 직접 작성 (양극 구조 활용)

ST4, ST5                    ← 삭제 (현행 모델에 없는 facet)
VIA / MPQ 보강              ← 불필요해져 폐기
```

**ST3에 VIA Spirituality를 쓰지 않는 이유** — 우리는 어차피 모든 문항을 직접 씁니다. IPIP 프록시는 "어떤 내용의 문항이 이 척도와 상관이 높은가"를 알려주는 참고자료지 필수품이 아닙니다. ST3는 **한국판 공식 facet 정의와 원전 구성개념 서술**을 근거로 직접 쓰는 편이 깨끗하고, 출처도 IPIP 하나로 통일됩니다.

**사내 맥락 대응** — ST3 문항은 종교색을 배제하고 의미·목적·연결감 중심으로 작성합니다.

```
✗ "나는 신이나 초자연적 존재를 믿는다"
✓ "나는 내가 하는 일이 나 개인을 넘어선 의미를 갖는다고 느낀다"
✓ "설명하기 어렵지만 분명히 느껴지는 순간들이 있다고 생각한다"
✓ (역채점) "세상의 모든 일은 결국 과학으로 설명될 수 있다고 본다"   ← 합리적 유물론 극
```

#### 2.9.5 부수 소득 — 문항 수 근거 (D-07)

**TCI-140은 영역당 20문항으로 α .84~.89를 얻었습니다.** 우리 계획은 영역당 15문항으로 같은 구간입니다. 105문항 배정이 실증적으로 타당하다는 근거가 확보됐습니다.

#### 2.9.6 ⚠️ 함께 기록해야 할 한계

같은 논문의 결론입니다.

> TCI-R의 가설적 **7요인 구조는 확인적 요인분석에서 지지되지 않았습니다** (CFI .71, TLI .67, RMSEA .11, SRMR .12). 저자들은 하위척도 수준의 분석이 **"제한적 유용성"**에 그친다고 결론냈습니다. TCI-140도 문항-영역 배정이 지지되지 않았고, 특히 HA/SD, HA/NS 문항이 잘 분화되지 않았습니다.

**정식 TCI조차 7요인 구조가 일반 성인 표본에서 잘 재현되지 않습니다.** 자체 제작 도구가 그보다 나을 이유는 없습니다.

**설계 함의 → U-05 결정으로 이어짐**

| 함의 | 조치 |
|---|---|
| 하위척도 수준을 신뢰하기 어려움 | ✅ **사원 결과 화면은 7대척도까지만.** 하위척도는 DB에 저장하되 관리자 문항분석에만 사용 |
| HA/SD, C/RD 구분이 흐릿함 | 해설에서 두 척도를 대비시키는 문장을 조심해서 작성 |
| 우리 데이터로 검증 필요 | 운영 중 α 모니터링(F-23)이 유일한 실질 검증 수단 |

|---|---|
| 화면의 "필수" 표현 | **넣지 않음** — 시작 화면·안내문·관리자 화면 전부 |
| 독려 알림 / 리마인더 발송 | **만들지 않음** (F-10에서 해당 기능 제외) |
| 미응시 현황 표시 | **유지** — 관리자가 응시율을 알 필요는 있음. 단 표시만 하고 행동은 유발하지 않음 |
| 마감일 / 카운트다운 | 넣지 않음 |
| 운영 정책 | 회사가 사내 공지 등으로 별도 결정. **시스템 밖의 일** |

**이 결정이 리스크에 유리하게 작용합니다**

기술검토서 §9가 응답 왜곡 완화 옵션으로 "응시를 자발적 참여로 운영"을 제시했습니다. 시스템이 "필수"를 박아두지 않으면 그 옵션이 열려 있는 상태로 유지됩니다. 반대로 UI에 "필수 응시"를 넣으면 나중에 정책을 바꿔도 화면을 고쳐야 합니다.

> 💡 **선택 여지 (미결정, U-06)**: 시작 화면에 **"참여 여부는 자유입니다"를 명시**할지 여부. 명시하면 응답 왜곡이 더 줄어들 수 있으나, 이는 회사가 아직 내리지 않은 정책 선언이므로 **지금은 중립(언급 없음)**으로 둡니다. 회사 방침이 정해지면 문구 한 줄 추가로 대응 가능합니다.

### 3.4 구간 판정 기준 — ⚠️ 근거 없음, 우리가 정해야 하는 값 (D-26)

**이 프로젝트에서 유일하게 "학술 근거 없이 우리가 임의로 정하는 값"입니다.** 다른 모든 요소(7척도 구조, 하위척도 명칭, 큐브 8유형, 역채점 방식)는 논문이나 공개 자료에 근거가 있지만, 이것만은 없습니다. 그래서 별도 절로 분리해 눈에 띄게 기록합니다.

**무엇이 없는가**

정식 검사는 수천 명 표준화 표본으로 점수 분포를 구해 "이 점수는 상위 몇 %"라는 환산표(규준, norm)를 만듭니다. **우리는 문항을 새로 썼기 때문에 그 문항에 사람들이 실제로 몇 점을 주는지 아무도 모릅니다.** 따라서 "62%가 높은 편인가?"에 답할 근거가 없습니다.

**무엇을 정해야 하는가**

```
척도 점수(만점 대비 %)  →  [경계값 ???]  →  lower / middle / upper
```

이 경계값이 정해져야 결과 화면의 구간별 서술(A+B)과 큐브 유형 판정(§2.2)이 작동합니다. **경계가 바뀌면 사람들의 구간이 통째로 바뀝니다.**

**확정값**

| | 값 | 상태 |
|---|---|---|
| 경계값 | `50% 미만 = lower` / `65% 초과 = upper` / 그 사이 = `middle` | ✅ **확정 (보정판).** 여전히 학술 근거는 없는 임의값이지만, 아래 문제를 최소화하도록 보정함 |

**왜 40/60이 아니라 50/65인가**: 7점 척도에서 모든 문항에 중립(4점)을 답하면 `4/7 = 57.1%`가 나옵니다. 40/60 경계였다면 이 **중립 응답자가 `upper`로 잘못 분류**될 뻔했습니다. 50/65로 올리면 57.1%가 `middle` 범위(50~65%) 안에 정확히 들어와, **적어도 "중립적으로 답한 사람이 middle에 못 들어가는" 명백한 오류는 피합니다.**

> ⚠️ 그렇다고 근거 있는 값이 된 건 아닙니다 — 여전히 "우리가 정한 임의 기준"입니다. §2.10 검사 명칭 절과 마찬가지로, 이 사실을 결과 화면에서 숨기지 않습니다(아래 참조).

**언제 어떻게 재조정하는가**

응답이 30건 이상 쌓이면 실제 분포를 확인할 수 있습니다. 그때 관리자 화면(`01` §4.2)의 척도별 분포를 보고 경계를 다시 조정합니다.

| 조정 방식 | 내용 |
|---|---|
| 고정 경계 재조정 | 실제 분포를 보고 50/65를 다른 값으로 변경 |
| 사내 분포 기준 전환 | 사내 평균±표준편차 기준으로 판정 |

**이미 결과를 본 사람은 영향받지 않습니다** — §2.6 스냅샷 원칙에 따라 기존 결과는 고정되고, 경계 변경 후 새로 응시하는 사람부터 적용됩니다.

**결과 화면에 반드시 명시할 것**

구간 판정이 임의 기준이라는 사실을 사원에게 숨기지 않습니다. 결과 화면 하단 고지문(`01` §3.2)에 이 내용을 포함합니다 — "구간 구분은 사내 자체 기준이며 공인된 규준이 아닙니다".

### 3.6 데이터 백업 — ✅ 확정 (D-28, 2026-08-21 신규)

> ⚠️ **검토 중 발견된 누락입니다.** 설계 문서 어디에도 백업·복구가 없었습니다. 서버 한 대에 DB 하나를 두는 구조인데 그 디스크가 죽으면 **전원의 응답과 결과가 소실**되고, 되살릴 방법이 50명에게 재응시를 시키는 것뿐입니다. 그마저도 첫 응답과 다른 결과가 나옵니다.

**두 겹으로 갑니다.**

| | 방식 | 목적 |
|---|---|---|
| **자동** | 매일 1회 `pg_dump`로 덤프 생성, 서버 내 볼륨에 보관. **최근 14개만 유지**하고 오래된 것부터 삭제 | 실수로 지웠거나 데이터가 깨졌을 때 되돌리기 |
| **수동** | 관리자 화면 버튼 → 백업 파일 즉시 생성 후 내려받기 | **서버 자체가 죽는 상황 대비.** 파일을 서버 밖에 둘 수 있어야 실질적 방어가 됨 |

**자동 백업을 별도 스케줄러 없이 구현합니다** — F-31(오래된 미완료 세션 정리)과 같은 방식입니다. 관리자가 대시보드를 열 때 "마지막 백업이 24시간 이상 지났는가"를 확인하고, 지났으면 그 자리에서 덤프를 만듭니다. cron이나 별도 프로세스를 두지 않아도 되고, 관리자가 한 달간 안 들어와도 사원 로그인 시점에도 같은 검사를 겁니다.

```ts
const BACKUP_INTERVAL_HOURS = 24
const KEEP_COUNT = 14

export async function ensureBackup(): Promise<void> {
  const last = await latestBackupTime()   // 백업 디렉터리의 최신 파일 시각
  if (last && Date.now() - last.getTime() < BACKUP_INTERVAL_HOURS * 3600_000) return
  await runPgDump()
  await pruneOldBackups(KEEP_COUNT)
}
```

백업 파일에는 **전화번호를 포함한 모든 원본 데이터**가 들어 있어 CSV 내보내기보다 민감합니다. 화면에 안전한 보관을 당부하는 안내를 함께 띄웁니다. (D-29로 감사 로그가 없어져 다운로드 이력은 남지 않습니다.)

> ⚠️ **백업 파일은 CSV와 성격이 다릅니다.** CSV는 분석용이라 전화번호를 뺐지만, 백업은 복구용이라 전부 들어갑니다. 관리자 화면에 이 사실을 명시하고, 파일을 안전하게 보관해야 한다는 안내를 함께 띄웁니다.

**복구는 문서로만 남깁니다.** 화면에서 복구 버튼을 제공하지 않습니다 — 잘못 누르면 현재 데이터를 덮어쓰는 되돌릴 수 없는 동작이고, 실제로 쓸 일은 몇 년에 한 번입니다. 복구 절차(`psql < backup.sql`)를 운영 문서에 적어두는 편이 안전합니다.

### 3.7 헷갈리기 쉬운 두 가지 숫자 — 용어 정리

문서 곳곳에 "30"이라는 숫자가 나오는데 **서로 다른 것**이라 분리해 적어둡니다.

| | 무엇을 재나 | 무엇과 무관한가 | 어디에 나타나나 |
|---|---|---|---|
| **응시 인원 (n)** | 몇 명이 응시를 마쳤는가 | 문항 품질과 무관 | 관리자 요약 카드 (전체 / 완료 / 진행중 / 미응시) |
| **Cronbach's α** | 한 척도의 문항들이 서로 맞물려 같은 것을 재는가 | **응시 인원과 무관** | 관리자 "검사 품질" 카드 |

**α가 무엇인가**

한 척도(예: NS 자극추구)에 15문항이 들어갑니다. 문항이 잘 만들어졌다면 자극추구가 높은 사람은 15문항 대부분에 높게 답하고, 낮은 사람은 대부분에 낮게 답합니다 — 응답이 서로 맞물립니다. 이때 α가 높습니다.

어떤 문항이 애매해서 사람마다 다르게 해석하면 그 문항만 응답이 흩어지고, 나머지 14문항과 맞물리지 않습니다. α가 떨어지고 이는 **"이 척도 점수를 믿기 어렵다"**는 신호입니다.

**100명이 해도 문항이 나쁘면 α는 낮고, 30명이 해도 문항이 좋으면 α는 높습니다.** 다만 α를 *계산하려면* 최소 30건 정도의 응답이 필요합니다 — 이건 별개의 이유입니다.

**"30"이 두 군데 나오는 이유**

| 항목 | 30의 의미 |
|---|---|
| D-42 | 사내 상대위치를 계산할 만큼 **사람이 모였는가** (10명, D-24를 대체) |
| F-23 / U-04 | α를 계산할 만큼 **데이터가 모였는가** |

기준이 우연히 비슷할 뿐 서로 다른 판단입니다.

## 4. 남은 미결정 — 전부 운영 정책, 개발 착수를 막지 않음

| # | 질문 | 성격 |
|---|---|---|
| **U-04** | α(문항 신뢰도)가 `.7` 미만인 척도의 결과 표시를 약하게 할지 | 어느 척도가 미달일지는 데이터가 쌓여야 알 수 있음. **응시 인원과는 무관한 지표** — §3.5 용어 정리 참조 |
| **U-06** | 시작 화면에 "참여 여부는 자유입니다"를 명시할지 | 회사 방침이 정해지면 문구 한 줄 추가 (§2.11) |
| **U-10** | 로그인 화면 고지문의 **보관 기간 문구** | D-14는 "로그인 화면에서 고지"로 확정됐으나, 몇 년/몇 개월로 쓸지는 회사가 정할 사안. 정해지면 문구 한 줄 채우면 됨 |

**해소된 항목** — D-22(문항 배분)는 §2.9에서 하위척도 구성이 확정되며 소멸. D-23(파일럿)은 §3.4에서 운영 중 검증으로 대체 확정. D-24(관리자 화면 상대위치 노출 기준)는 잠정 30명으로 §1로 이동. **D-25(A안 확정)·D-27(PIN 미도입)은 D-05 "이름+전화번호만" 확정과 함께 §1에서 정리 완료.**

## 5. 리스크 — 계속 눈에 띄게 둘 것

| 리스크 | 현재 대응 |
|---|---|
| **응답 왜곡 (faking good)** | 실명 응답 + 관리자 열람 구조라 왜곡 가능성이 있음. **완화 수단을 두지 않기로 함 (2026-08-21).** 익명 모드 제외(§2.8), 감사 로그 제거(D-29), 첫 화면 고지문도 담백한 안내로 축소. 왜곡을 감수하고 단순함을 택한 것이며, 결과를 참고 자료로만 쓴다는 전제에서 수용 가능하다고 판단 |
| **동료 사칭 (이름+전화번호로 남의 결과 열람)** | **사원 계정에 한해 구조적으로 열려 있음 — 감수 확정(D-27).** 사내에서 이름·전화번호는 비밀이 아니므로 아는 사람이면 남인 척 로그인 가능. **단 D-05 변경으로 관리자 계정은 비밀번호로 보호되어, "한 명이 전원 데이터를 가져가는" 최악 시나리오는 차단됨.** 남은 완화 요소는 ① 사내 서버 배포(D-04) ② 반복 시도 차단. 근본 해결은 사원 인증도 교체(사번+비밀번호/SSO) — 필요해지면 `lib/auth/`만 고치면 됨 |
| **관리자 계정 탈취** | 비밀번호 인증(D-05) + 실패 5회 잠금(5분). **감사 로그를 제거(D-29)해 사후 추적 수단은 없음** — 예방에만 의존 |
| **데이터 소실 (서버 장애)** | 서버 한 대 구성이라 디스크가 죽으면 전원의 응답·결과가 사라짐. 재응시로는 복구 불가(첫 응답과 달라짐). → **자동 일 1회 백업 + 관리자 수동 내려받기**(D-28, §3.6). 수동 백업본을 서버 밖에 두는 것이 실질적 방어 |
| **표본 부족** | 50명 이내. 부서별 비교 제외(❌). 상대위치는 응시 10명 이상일 때만(D-42), 참고용 표기 병행 |
| **7요인 구조 재현성** | 정식 TCI조차 CFA에서 7요인 구조가 지지되지 않음(CFI .71, RMSEA .11). → 사원 화면은 7대척도까지만(U-05), 하위척도 해석 금지 |
| **문항 타당도 미검증** | 자체 문항이라 α·문항총점상관이 미지수. 별도 파일럿 없이 **운영 중 α 모니터링(F-23) → v2 개정**으로 대응. 초기 약 30명은 미검증 문항 결과를 받게 됨 |
| **라벨링 사고** | §2.2대로 논문 라벨 전부 버리고 서술문만. 코드 레벨에서 유형명 필드를 아예 안 만듦 |
| **저작권** | 정식 TCI 문항 미사용, "TCI" 명칭 미사용(D-12), 문항별 근거 출처 기록으로 자체 작성 입증 |

## 8. 기술 스택 확정

```
Next.js 16 (App Router) + TypeScript
PostgreSQL 16 + Prisma
Tailwind CSS + shadcn/ui
Recharts (레이더 차트)
React Hook Form + Zod (응답 검증)
Vitest (채점 엔진 테스트)
Docker Compose (app + postgres)
next.config: output 'standalone'
```

`standalone` 빌드로 가면 이미지가 작아지고 사내 서버 이관이 단순해집니다. 환경변수는 `process.env`로 직접 읽습니다(standalone에서는 `runtimeConfig`가 동작하지 않습니다).
