## 1. 실제로 뜯어본 것

문서로 읽은 게 아니라 브라우저로 열어서 직접 확인한 내용입니다.

### 1.1 16Personalities — 완성도 기준선

전 세계에서 가장 많이 쓰이는 성격검사 사이트입니다. 실제로 열어서 확인한 사양:

| 항목 | 실제 구현 |
|---|---|
| 총 문항 | **60문항** |
| 페이지당 문항 | **6문항** → 총 10페이지 |
| 응답 척도 | **7점**, Agree ↔ Disagree |
| 척도 UI | **크기가 다른 원 7개.** 양 끝이 가장 크고 가운데(중립)가 가장 작음 |
| 색상 | 동의쪽 초록 / 중립 회색 / 비동의쪽 보라 |
| 숫자 표기 | **없음.** 양 끝에만 "Agree" / "Disagree" 라벨 |
| 진행률 | 화면 최상단 얇은 가로 바 |
| 접근성 | 각 문항에 숨김 텍스트 `"Question 1 of 60: You regularly make new friends."` |
| 이동 | 6문항 아래 `Next →` 버튼 |

**가장 중요한 발견 — 포커스/디밍 패턴**

한 페이지에 6문항이 다 보이는데, **현재 답할 문항만 진하고 나머지는 흐릿하게** 처리돼 있습니다. 하나를 답하면:

1. 그 문항에 체크가 채워지고 → **그 줄이 흐려짐**
2. **다음 문항이 진해짐**
3. 화면이 살짝 자동 스크롤

즉 "한 번에 한 문항"의 집중력과 "스크롤 목록"의 속도를 동시에 가져갑니다. 별도의 다음 버튼 없이 **답하는 행위 자체가 진행**입니다.

### 1.2 bigfive-test.com — 오픈소스 대조군

`bigfive-web` 저장소(★937)의 실서비스. Next.js로 만들어졌고 **한국어를 지원**합니다.

| 항목 | 실제 구현 |
|---|---|
| 응답 척도 | **5점**, 세로 라디오 버튼 목록 |
| 라벨 | **전 항목 라벨 표기** — 매우 그렇지 않다 / 그렇지 않다 / 보통이다 / 그렇다 / 매우 그렇다 |
| 진행률 | 상단 가로 바 + **퍼센트 숫자** + **경과 타이머(00:06)** |
| 문항 표시 | 한 화면에 여러 문항, 디밍 없음 |
| 한국어 문항 어투 | `"나는 걱정이 많은 편이다."` `"나는 쉽게 친구를 사귀는 편이다."` |

**여기서 가져올 것 / 버릴 것**

- ✅ **전 항목 라벨 표기** — 한국어 설문 관행이고, 숫자만 있는 척도보다 응답자가 덜 헷갈립니다. 단 **단계 수는 5점이 아니라 7점을 채택**했습니다 (§2.2 근거 참조)
- ✅ **문항 어투** — "나는 ~한 편이다"는 우리 문항 작성 시 참고할 어투 (단, 저작권 문서 §2.4가 금지한 건 *원문항의 어미만 바꾸는 것*이지 어투 관행 자체가 아닙니다)
- ❌ **경과 타이머** — 시간이 눈앞에서 흐르면 서두르게 됩니다. 우리는 불성실 응답을 잡으려는 쪽이라 정반대로 작동합니다. **넣지 않습니다**

## 2. 응시 화면 설계

### 2.1 문항 제시 방식

**[벤치마크]** 16Personalities는 6문항/페이지 + 디밍, bigfive-test는 전체 스크롤, Typeform은 1문항/화면.

**[판단]**
- 연구상 데스크톱에서는 페이징과 스크롤의 완주율 차이가 크지 않습니다. **모바일에서는 페이징이 유리**하지만 완료 시간이 길어집니다.
- 대화형(1문항 1화면)은 12~14문항이 한계라 105문항엔 못 씁니다.
- 스크롤에서는 **문항을 건너뛰는 비율이 올라간다**는 결과가 있습니다 → 디밍으로 억제 가능.

**[우리 설계]**

```
척도 단위 섹션 7개로 분할
  ↓
각 섹션 안에서 문항을 세로로 나열
  ↓
현재 문항만 진하게, 나머지는 흐리게 (16Personalities 패턴)
  ↓
답하면 자동으로 다음 문항이 활성화 + 부드러운 스크롤
  ↓
섹션 끝에서 "다음 섹션" 버튼 → 이때 서버 저장
```

**섹션 길이를 앞쪽부터 짧게 배치합니다.** 이건 그냥 정한 게 아니라 근거가 있습니다 — 진행률 지표 메타분석에서 **초반이 빠르게 차오르는(fast-to-slow) 방식은 이탈을 줄이고, 반대는 이탈을 늘립니다.** 일정 속도는 효과가 없습니다.

문항 수를 조작해서 가짜로 빠르게 보이게 하는 건 정직하지 않으니, **실제로 앞 섹션을 짧게 만듭니다.**

| 섹션 | 척도 | 문항 수 (105문항 기준 예시) |
|---|---|---|
| 1 | NS 자극추구 | 12 |
| 2 | HA 위험회피 | 13 |
| 3 | RD 사회적 민감성 | 15 |
| 4 | PS 인내력 | 15 |
| 5 | SD 자율성 | 16 |
| 6 | CO 연대감 | 17 |
| 7 | ST 자기초월 | 17 |

첫 섹션이 12문항이라 "1/7 완료"가 빨리 뜨고, 뒤로 갈수록 느려집니다. 정직하면서 fast-to-slow입니다.

> ⚠️ **주의**: 척도별 문항 수가 달라지면 **원점수를 척도 간에 직접 비교할 수 없습니다.** 만점 대비 %로 환산해서 표시해야 합니다. (채점 설계에 반영 필요)

### 2.2 응답 척도 UI

**[판단]** 16Personalities의 크기 다른 원은 예쁘지만 두 가지 문제가 있습니다.

1. **색맹 대응** — 초록/보라로 방향을 구분하는데, 이건 기술검토서 §18.2가 지적한 문제와 같습니다
2. **숫자·라벨 없음** — 가운데 3개 원의 의미가 모호합니다. "약간 동의"인지 "잘 모르겠음"인지 구분이 안 됩니다

**[우리 설계]** — ✅ **7점**, 전 항목 라벨, 가로(데스크톱)/세로(모바일)

> **7점 채택 근거 (U-01 확정)**
>
> 초안에서는 5점을 제안했으나(bigfive-test 벤치마크를 따름), 문헌 확인 결과 근거가 약해 **7점으로 정정**했습니다.
>
> | 근거 | 내용 |
> |---|---|
> | Krosnick & Presser 종합 검토 | **단극 척도는 5점, 양극 척도는 7점**이 최적 |
> | 우리 척도의 성격 | `아니다 ↔ 보통 ↔ 그렇다`는 양극 척도 → 7점 해당 |
> | 내적 일관성 | 7점이 5점보다 신뢰도가 높게 나옴. **표본 50명 이내라 분산 확보가 특히 중요** |
> | 5점 미만 / 7점 초과 | 5점 미만은 신뢰도 하락, 7점 초과는 이득 미미 + 인지 부담 |
>
> **출처와의 궁합**: IPIP 공식 안내는 문항 수정·번역과 함께 **"원하는 만큼의 응답 단계 사용"을 명시적으로 허용**합니다. 7점 사용에 제약 없음.
>
> **비용**: ① 역채점 공식이 `6 - value` → `8 - value` ② 좁은 폭에서 세로 스택 시 한 문항이 화면을 거의 다 차지함 → **PC 우선(U-03) 확정으로 실질 비용 해소.** 반응형 정책은 §2.3
>
> **IPIP 공개 α값은 원래도 차용 불가**입니다 — 한국어로 새로 쓰는 문항이라 영어 원문항의 신뢰도는 전이되지 않습니다. 7점 전환이 이 점을 악화시키지 않습니다.

```
데스크톱 (가로 배치)

  나는 처음 가보는 장소에 가는 것을 좋아한다.

  ○ 전혀   ○ 아니다  ○ 약간   ○ 보통  ○ 약간   ○ 그렇다  ○ 매우
    아니다            아니다            그렇다             그렇다


좁은 폭 / 모바일 (세로 배치 — §2.3 분기)

  나는 처음 가보는 장소에
  가는 것을 좋아한다.

  ┌────────────────────────┐
  │ ○  전혀 아니다          │   ← 최소 44px 높이
  ├────────────────────────┤
  │ ○  아니다               │
  ├────────────────────────┤
  │ ○  약간 아니다          │
  ├────────────────────────┤
  │ ○  보통                 │
  ├────────────────────────┤
  │ ○  약간 그렇다          │
  ├────────────────────────┤
  │ ○  그렇다               │
  ├────────────────────────┤
  │ ●  매우 그렇다          │
  └────────────────────────┘
```

**대안 라벨 — 정확도형**: IPIP의 원래 응답 형식은 동의가 아니라 정확도입니다 (`매우 부정확하다 ~ 매우 정확하다`, "이 문장이 나를 얼마나 정확히 묘사하는가"). 어느 쪽도 유효하나, 한국어로는 동의형이 자연스러워 동의형을 채택합니다.

**규칙**
- 세로가 두 기기 모두에서 안전하지만, 데스크톱에서 105문항을 세로로 두면 스크롤이 5배가 됩니다 → **반응형으로 분기**
- 방향은 **색이 아니라 위치와 라벨**로 표현. 색은 보조 수단으로만
- 터치 타깃 **최소 44×44px** (WCAG 2.2 SC 2.5.8은 24×24px가 최소지만, 실사용 권장은 44px)
- 선택된 항목은 **색 + 굵기 + 체크 표시** 세 가지로 동시에 표현 (색맹 대응)

### 2.3 반응형 정책 — PC 우선, 해상도 유연 (U-03 확정)

**✅ 결정: PC 기반으로 만들되 고정폭이 아닌 유동 레이아웃. 모바일 최적화는 후순위이나 깨지지는 않게.**

**노트북에서 실제로 문제가 되는 것 — 화면 배율**

사내 PC 환경에서 가장 흔한 함정입니다. 1920×1080 노트북이라도 Windows 디스플레이 배율이 150%면 **브라우저가 보는 실제 폭은 1280px**입니다. 125%면 1536px입니다. 즉 "요즘 다 FHD니까 1920 기준으로 짜면 된다"가 성립하지 않습니다.

| 실제 해상도 | 배율 | 브라우저 유효 폭 |
|---|---|---|
| 1920×1080 | 100% | 1920 |
| 1920×1080 | **125%** | 1536 |
| 1920×1080 | **150%** | **1280** |
| 1366×768 (구형 노트북) | 100% | 1366 |
| 2560×1440 | 150% | 1707 |

→ **설계 하한을 1280px가 아니라 1024px로 잡습니다.** 여유를 두는 게 아니라, 이 범위가 실제로 존재합니다.

**대상 범위**

| 구간 | 폭 | 이번에 하는 것 |
|---|---|---|
| 대형 모니터 | 1600px+ | ✅ 여백 활용, 콘텐츠는 안 늘어남 |
| 일반 데스크톱·노트북 | 1024~1599px | ✅ **주 대상** |
| 태블릿·좁은 창 | 768~1023px | ✅ 깨지지 않게만 |
| 모바일 | ~767px | 🔜 나중. **단 구조는 지금 준비** |

**핵심 원칙 — 고정 px을 쓰지 않습니다**

```css
/* ✗ 이렇게 하지 않음 */
.container { width: 1200px; }
.item-text { font-size: 16px; }

/* ✓ 이렇게 */
.container {
  width: 100%;
  max-width: 46rem;        /* 읽기 폭 제한 — 아래 설명 */
  margin-inline: auto;
  padding-inline: clamp(1rem, 4vw, 3rem);
}
.item-text {
  font-size: clamp(1rem, 0.9rem + 0.4vw, 1.25rem);
}
```

**문항 영역에 `max-width`를 거는 이유** — 화면이 넓다고 문항 텍스트를 화면 끝까지 늘리면 오히려 읽기 어려워집니다. 한 줄이 길어지면 다음 줄 첫 글자를 찾느라 눈이 헤맵니다. 한국어 기준 **한 줄 40~50자 정도가 상한**이라 `max-width`로 제한하고 남는 공간은 여백으로 둡니다.

**단, 관리자 표는 반대입니다.** 사원 목록·통계 표는 넓은 화면을 최대한 씁니다. `max-width` 없이 전체 폭을 쓰고, 좁아지면 `overflow-x: auto`로 가로 스크롤합니다.

| 영역 | 폭 정책 |
|---|---|
| 응시 화면 · 결과 화면 | `max-width` 제한 + 가운데 정렬 (가독성) |
| 관리자 목록 · 통계 | 전체 폭 사용 + 좁아지면 가로 스크롤 |

**7점 척도의 반응형 분기 — 여기가 유일한 실질 작업**

```
폭 ≥ 1024px      가로 7개 + 라벨 전체 표기
                 ○전혀아니다 ○아니다 ○약간아니다 ○보통 ○약간그렇다 ○그렇다 ○매우그렇다

폭 768~1023px    가로 7개 유지 + 라벨 2줄 줄바꿈
                 ○전혀   ○아니다  ○약간   ○보통  ○약간   ○그렇다  ○매우
                   아니다           아니다          그렇다           그렇다

폭 < 768px       세로 스택 (모바일)
                 ┌──────────────┐
                 │ ○ 전혀 아니다 │
                 ├──────────────┤
                 │ ○ 아니다      │
                 │ ...           │
```

> 💡 **세로 스택을 지금 만들어둡니다.** 모바일은 후순위지만, 이 분기는 **CSS 미디어쿼리 한 블록**이라 지금 넣는 비용이 거의 0입니다. 반대로 나중에 넣으려면 컴포넌트 구조를 뜯어야 합니다. **"추후 모바일 가능"을 실제로 싸게 만드는 유일한 방법이 지금 구조를 열어두는 것입니다.**

**부수 효과 — 접근성이 공짜로 따라옵니다**

WCAG 1.4.4는 **200% 확대에서도 내용 손실 없이 사용 가능**할 것을 요구합니다. 브라우저 200% 확대는 유효 폭을 절반으로 줄이는 것과 같아서, 1600px 창이 800px이 됩니다. **유동 레이아웃으로 만들면 이 요구사항이 저절로 충족됩니다.** 고정폭으로 만들면 별도 작업이 됩니다.

**구현 수단**

| 용도 | 방법 |
|---|---|
| 폭 | `%`, `max-width` + `rem`, `clamp()` |
| 여백 | `clamp(1rem, 4vw, 3rem)` |
| 글자 | `clamp()` 유동 타이포그래피 |
| 배치 | Flexbox / CSS Grid `auto-fit` |
| 분기 | Tailwind 기본 브레이크포인트 (`md:` 768 / `lg:` 1024 / `xl:` 1280) |
| 차트 | Recharts `<ResponsiveContainer>` + 고정 종횡비 |
| 표 | 컨테이너에 `overflow-x: auto` |

**검증 방법**

개발 중 다음 폭에서 한 번씩 확인합니다 — `1024` / `1280` / `1440` / `1920`, 그리고 **브라우저 200% 확대**. 실제 노트북 배율 문제는 1280 확인으로 대부분 잡힙니다.

### 2.4 접근성 — 이건 타협하지 않습니다

사내 전 직원이 응시하므로 스크린리더·키보드 사용자가 있을 수 있습니다.

**[벤치마크]** 16Personalities는 각 문항에 숨김 텍스트로 `"Question 1 of 60: <문항>"`을 넣어뒀습니다. 좋은 패턴이라 그대로 가져옵니다.

**[우리 설계]**

```html
<fieldset>
  <legend>
    <span class="sr-only">3번 문항, 전체 105문항 중.</span>
    나는 처음 가보는 장소에 가는 것을 좋아한다.
  </legend>

  <input type="radio" id="q3-1" name="q3" value="1">
  <label for="q3-1">전혀 아니다</label>
  ...
</fieldset>
```

| 요구 | 구현 |
|---|---|
| WCAG 1.3.1 — 그룹 관계 | `<fieldset>` + `<legend>`. **`<legend>`는 fieldset의 첫 자식이어야 함** |
| 개별 라벨 | 각 라디오마다 `<label for>` |
| 위치 안내 | `sr-only`로 "N번 문항, 전체 M문항 중" |
| 키보드 | 네이티브 라디오 → 화살표키가 자동 동작. **커스텀 div로 만들면 이걸 직접 구현해야 하므로 네이티브를 씁니다** |
| 포커스 표시 | 디밍된 문항도 키보드 포커스가 가면 즉시 활성화 |
| 색 의존 금지 | 위치·라벨·체크표시 병행 |

> **설계 원칙**: 라디오 버튼을 `div`로 커스텀 구현하지 않습니다. 네이티브 `<input type="radio">`에 CSS만 입힙니다. ARIA를 나중에 덧대는 것보다, 처음부터 의미 있는 HTML을 쓰는 게 안전합니다.

### 2.6 자동저장 / 이어하기

**[판단]** 문항마다 서버로 보내면 105번 왕복입니다. 기술검토서 §18.2도 섹션 단위 배치 저장을 지정했습니다.

**[우리 설계]** — 2단 저장

```
   [1단] 문항 응답 → 즉시 localStorage
          목적: 브라우저 사고(새로고침, 탭 닫힘) 방어
          비용: 0

   [2단] 섹션 완료 → 서버 POST (배치)
          목적: 기기 변경, 진짜 이어하기
          횟수: 7번
```

**이어하기 판정 흐름**

```
로그인
  ↓
서버에 진행 중(in_progress) 세션이 있나?
  ├ 없음 → 새 세션 생성 → 섹션 1
  └ 있음 → localStorage에 더 최신 응답이 있나?
             ├ 있음 → "○○님, 5번 문항까지 답하셨습니다. 이어서 하시겠어요?"
             └ 없음 → 서버 기준으로 마지막 섹션부터
```

**예외 처리** (기술검토서 §18.1 반영)

| 상황 | 처리 |
|---|---|
| 응시 중 문항 개정 | 세션 생성 시 `assessment_version` **고정(pin)**. 진행 중인 사람은 기존 버전으로 완주 |
| 두 기기 동시 접속 | 마지막 저장이 이김(last-write-wins) + 경고 표시 |
| 오래된 미완료 세션 | 30일 경과 시 `abandoned`로 전환. 관리자 화면에 노출 — 구현 방식은 아래 |

#### 30일 경과 세션 처리 — 별도 배치 없이 (F-31 확정)

전용 스케줄러(cron)를 두지 않습니다. 대신 **이미 호출되는 함수 두 곳에 검사 한 줄을 끼워 넣는 방식**입니다.

```ts
// lib/session-service.ts
const STALE_DAYS = 30

export async function sweepStaleSessions(employeeId?: string): Promise<void> {
  const cutoff = new Date(Date.now() - STALE_DAYS * 24 * 60 * 60 * 1000)
  await db.testSession.updateMany({
    where: {
      status: 'IN_PROGRESS',
      startedAt: { lt: cutoff },
      ...(employeeId ? { employeeId } : {}),
    },
    data: { status: 'ABANDONED' },
  })
}
```

| 호출 위치 | 범위 | 왜 여기서 |
|---|---|---|
| `getOrCreateSession(employeeId)` 맨 앞 | 이 사원 1명만 | 30일 넘게 방치했던 사람이 다시 로그인하면, 옛날 진행 중 세션을 먼저 정리하고 **새 세션으로 처음부터 시작**하게 함 |
| 관리자 대시보드 요약(`getSummary()`)·사원 목록(`listEmployees()`) 맨 앞 | 전체 | 아무도 다시 로그인 안 해도, **관리자가 화면을 볼 때마다 "진행중" 숫자가 정확해짐** |

배치 작업도, 별도 인프라도 필요 없습니다 — 이미 호출되는 두 함수 앞에 한 줄씩 추가하는 것뿐입니다.

### 2.7 문항별 응답시간 기록

`00_설계_작업본.md` §2.3에서 채택한 품질 지표의 원자료입니다.

```ts
// 클라이언트: 문항이 "활성" 상태가 된 시각부터 응답까지
type ResponseDraft = {
  itemId: string
  value: 1 | 2 | 3 | 4 | 5 | 6 | 7
  elapsedMs: number      // 활성화 → 클릭
  changedCount: number   // 답을 몇 번 바꿨는지
}
```

`changedCount`는 벤치마크에 없는 우리 추가 항목입니다. 여러 번 고친 문항은 **문항이 모호하다는 신호**라 문항 품질 개선 자료가 됩니다.

> 응시자에게는 이 기록을 알리지 않습니다 — 알면 의식해서 응답이 왜곡됩니다. 다만 §2.9의 사전 고지에 "응답 패턴이 기록된다"는 사실 자체는 포함합니다.

## 3. 결과 화면 설계

### 3.1 벤치마크가 하는 것과 우리가 못 하는 것

| 일반 성격검사 사이트 | 우리 |
|---|---|
| "당신은 INFP입니다" 유형명 대문짝 | ❌ **금지** — 라벨링 금지 원칙 |
| 백분위 ("상위 23%") | ❌ 규준 없음. 50명 이내라 사내 백분위도 불안정 |
| 유형별 캐릭터 일러스트 | ❌ 진단처럼 읽힘 |
| 레이더 차트 | ✅ 채택 — 다차원 프로파일의 사실상 표준 |
| 척도별 막대 | ✅ 채택 — 레이더는 비교가 어려워서 막대 병행 |
| 서술형 해설 | ✅ 채택 — 단 유형명 없이 |
| 하위척도 세부 점수 | ❌ **제외 (U-05)** — 아래 참조 |

> **하위척도를 사원에게 보여주지 않는 이유 (U-05 확정)**
>
> Farmer & Goldberg(2008)는 정식 TCI-R에서조차 **7요인 구조가 확인적 요인분석에서 지지되지 않았고**(CFI .71, RMSEA .11), **하위척도 수준의 분석은 "제한적 유용성"**에 그친다고 결론냈습니다. 원 검사가 신뢰하지 말라고 하는 층위의 숫자를 자체 제작 도구가 개인에게 제시하는 것은 곤란합니다.
>
> → **사원 결과 화면은 7대척도까지만.** 하위척도 점수는 DB에 저장하되 **관리자의 문항 분석 용도로만** 사용합니다. (`00_설계_작업본.md` §2.9.6)

**이게 설계상 가장 어려운 부분입니다.** 일반 검사 사이트가 재미를 만드는 장치(유형명, 캐릭터, 순위)를 전부 못 씁니다. 대신 **"내가 어떤 사람인지"가 아니라 "이 결과가 무엇을 보여주는지"**로 프레임을 바꿉니다.

### 3.3 서술문 작성 규칙 — 코드로 강제

기술검토서 §17의 금지 규칙을 문서에만 적어두면 지켜지지 않습니다. **데이터 구조로 강제합니다.**

```ts
// interpretation 데이터에 "유형명" 필드를 아예 만들지 않습니다
type ScaleNarrative = {
  scale: ScaleCode
  band: 'lower' | 'middle' | 'upper'   // high/low 아님 — 우열 함의 제거
  text: string
}
// ✗ 없음: typeName, label, category
```

| 쓰지 않음 | 대신 |
|---|---|
| "당신은 ~한 사람입니다" | "이 결과는 ~한 경향을 보여줍니다" |
| "높음 / 낮음" | "상대적으로 두드러짐 / 덜 두드러짐" |
| "미성숙", "취약" | (사용 금지) |
| "개선이 필요합니다" | "이런 상황에서 도움이 될 수 있습니다" |

`band` 값을 `high`/`low`가 아니라 `upper`/`middle`/`lower`로 두는 건 사소해 보이지만, **개발 중에 무심코 "높음"이라고 쓰게 되는 걸 타입 레벨에서 막습니다.**

### 3.3.1 1차 배포 범위 — 숫자만, 서술은 2차 (확정)

**✅ 결정: 1차 버전은 서술(A+B, Task 16) 없이 레이더+막대+원점수%만으로 출시합니다.** 서술은 별도 단계(Task 16)로 나중에 얹습니다.

| | 1차 | 2차 |
|---|---|---|
| 개인 결과(`/me`) | 레이더 + 막대 + % | + 척도 설명(A) + 구간별 서술(B) |
| 관리자 개인 상세 | 레이더 + 막대 + % + 품질지표 | + 동일 서술 |

**예외 — 척도 정의(A, 7개)만은 1차에 포함합니다.** §4.4에서 다루는 "클릭하면 설명 보기" 기능이 최소한 "이 척도가 뭘 재는지"는 알려줘야 하기 때문입니다. **개인별 맞춤 서술(B, 21개)과 큐브 조합(C, 16개)은 여전히 2차입니다.** A는 점수와 무관하게 항상 같은 문장(예: "자극추구란 무엇인가")이라 사람마다 다르게 쓸 필요가 없어 부담이 작습니다.

### 3.4 결과 공개 시점과 문항 검증 — U-02 / D-23 확정

**✅ 결정: 응시 직후 즉시 결과 표시. 별도 파일럿 단계는 두지 않음.**

**기술검토서가 제안했던 것 (§16, 2단계 배포)**

| 단계 | 내용 |
|---|---|
| 파일럿 20~30명 | 응시는 하되 **결과 미표시**, 응답만 수집 |
| 분석 | 척도별 Cronbach's α (0.7 이상 목표), 문항-총점 상관 (0.3 미만은 교체 후보), 응답 쏠림 |
| 개정 | 부적합 문항 교체 → assessment 버전 증가 |
| 정식 배포 | 결과 표시 활성화 |

**왜 우리는 그대로 못 하는가**

전체가 50명 이내입니다. 파일럿에 20~30명을 쓰면 본 검사에 남는 표본이 없습니다. 같은 사람이 두 번 응시하면 기억·연습 효과로 2회차가 오염됩니다. **50명 규모에는 별도 파일럿 집단이라는 것이 존재할 수 없습니다.**

**대안 — 파일럿을 없애지 않고 운영에 녹임**

```
정식 배포 (결과 즉시 표시)
        │
        │  응답 30건 누적
        ▼
관리자 "검사 품질" 카드 자동 활성화  ← F-23
   척도별 α · 문항-총점 상관 · 응답 쏠림
        │
        │  α < .7 인 척도 발견
        ▼
해당 척도 문항 교체 → assessment v2
   기존 v1 결과는 보존, 버전으로 구분
   진행 중 세션은 pin된 v1로 완주
```

> ⚠️ **v2 개정은 재응시를 뜻하지 않습니다 — 오해 방지**
>
> | | v1로 응시한 사람 | v2 이후 신규 응시자 |
> |---|---|---|
> | 재응시 요청 | **없음** | — |
> | 본인 결과 | v1 결과 그대로 유지 | v2로 채점 |
> | 관리자 화면 | 버전 표기 후 함께 조회 | |
>
> 버전 관리는 **관리자가 "이 사람은 v1, 저 사람은 v2"를 구분해 해석하기 위한 장치**이지, 사원에게 무언가를 다시 시키기 위한 것이 아닙니다. **한 번 응시하면 그것으로 끝입니다.**

파일럿의 목적(문항 품질 검증)은 달성하면서 표본을 낭비하지 않습니다. 이미 설계에 들어가 있는 세 가지가 이걸 지탱합니다 — **F-23 척도별 α 표시**, **문항 상태 워크플로(draft→review→active→retired)**, **세션의 assessment_version 고정(pin)**.

**치러야 할 값 (정직하게 기록)**

**초기 응시자 약 30명은 검증되지 않은 문항의 결과를 받습니다.** 이걸 완화하는 수단은 고지문뿐입니다.

| 조치 | 위치 |
|---|---|
| "사내 자체 제작 도구, 공인 심리검사 아님" | 시작 화면(§2.9) **+ 결과 화면 하단에도 상시 노출** |
| 유형명·라벨 없이 서술형만 | §3.3 |
| α가 기준 미달인 척도는 결과에서 해석 강도를 낮춤 | v2 개정 전까지 |

> 마지막 항목은 구현 여지가 있습니다 — `α < .7`인 척도는 결과 화면에서 서술을 짧게 하거나 "이 척도는 아직 안정적이지 않습니다" 표기를 붙이는 방법. **미결정(U-04)으로 둡니다.**

### 3.5 재응시 정책과 결과 확인 흐름 — D-10 (2026-08-21 변경)

> ⚠️ **기존 "1회 응시 원칙"을 뒤집었습니다.** 사용자 결정으로 **사원이 직접 재응시할 수 있게** 바뀌었습니다. DB는 원래부터 한 사원이 여러 세션을 갖는 구조라 스키마 변경은 없습니다.

**✅ 결정: 같은 이름+전화번호로 재로그인하면 이전 결과가 보이고, 결과 화면에서 직접 재응시 가능. 단 직전 응시로부터 30일 경과 필요. 이전 결과는 보존.**

```
로그인 → 고지문 → 7섹션 응시 → 제출 → 채점 → 결과 화면
                                                  │
       ┌──────────────────────────────────────────┤
       │                                          │
  [30일 미경과]                              [30일 경과]
  "다음 응시 가능: YYYY-MM-DD"              [다시 검사받기] 활성
                                                  │
                                                  ▼
                                          새 세션으로 처음부터
                                          (이전 결과는 이력에 남음)
```

| 항목 | 설계 |
|---|---|
| 제출 → 결과 | **끊김 없이 연결.** 중간 안내 화면이나 대기 화면 없음 |
| 결과 화면 체류 | **타이머·자동 리다이렉트 없음** |
| 재조회 | `/me`에서 언제든. **각 회차의 숫자는 달라지지 않음** — 스냅샷으로 고정 (§2.6) |
| **재검사 버튼** | **결과 화면 하단에 있음.** 30일 미경과 시 비활성 + 가능 일자 표시 |
| **재응시 간격** | **30일.** 근거: ① 즉시 재응시는 문항 기억으로 2회차가 오염됨 ② 원하는 결과가 나올 때까지 반복하는 것 방지 |
| **이력 보존** | 이전 결과 **삭제하지 않음.** 결과 화면 상단에서 응시 날짜를 선택해 과거 회차 조회 |
| 관리자 화면 기준 | 목록·분포·통계는 **최신 회차** 기준. 개인 상세에서 과거 회차 조회 가능 |
| 관리자 초기화 | 유지. **30일을 기다리지 않고 즉시 재응시시키는 수단**으로 역할이 바뀜 |

**"응시 → 결과"를 한 흐름으로 붙이는 이유**

제출 후 "제출되었습니다. 결과는 추후 안내드립니다" 같은 단절이 생기면 응시 자체가 행정 절차처럼 느껴집니다. 완주의 보상이 결과 화면인데 그 사이를 벌리면 보상이 사라집니다. 이 검사는 자발적 성실 응답에 전적으로 의존하므로, **결과를 바로 보는 것이 완주 동기이자 성실 응답 동기**입니다.

## 4. 관리자 화면 설계

### 4.0 관리자는 무엇을 하려고 이 화면에 오는가 — 설계 전제

관리자 화면의 목적이 정의되지 않은 채로 "데이터를 나열하는" 화면만 있으면, 42줄짜리 숫자표를 보고도 아무것도 읽어낼 수 없습니다. 먼저 **관리자가 답을 얻고 싶은 질문 4가지**를 정의하고, 각 질문이 어느 화면에서 해결되는지 매핑합니다.

| # | 관리자의 질문 | 어디서 해결 |
|---|---|---|
| **Q1** | 우리 회사 사람들은 전반적으로 어떤 성향인가? | §4.2 대시보드 — 전체 분포 |
| **Q2** | 누가 어떤 사람인지 훑어보고 싶다 | §4.3 목록 — 시각적 요약 + 정렬 |
| **Q3** | 특정 성향이 두드러진 사람은 누구인가? | §4.3 — 척도별 분포와 정렬 |
| **Q4** | 비슷한 사람끼리 묶이나? | §4.3 — 유형별 보기 |

> ⚠️ **이 화면들이 하는 일과 하지 않는 일**
>
> 관리자 화면은 **집계·정렬·시각화**만 합니다. 즉 "이 데이터가 이렇게 생겼다"를 보여주는 데까지입니다.
>
> **하지 않는 것**: "이 사람은 특이하다", "이 사람은 주의가 필요하다" 같은 판정. 우리 검사는 문항 타당도가 아직 검증되지 않았고(`00` §5), 정식 TCI조차 하위척도 수준 해석은 "제한적 유용성"이라는 평가를 받습니다(`00` §2.9.6). **그런 도구로 사람을 분류하는 기능을 시스템이 제공하면 안 됩니다.**
>
> 유일한 예외는 **응답 품질 플래그**입니다. 이건 성격에 대한 판정이 아니라 "이 응답 데이터를 신뢰할 수 있는가"에 대한 것이고, 연구로 검증된 지표(응답시간·역채점 일치도)에 근거합니다.

**핵심 설계 판단 — 화면을 늘리지 않고 하나에서 관점을 전환한다**

Q2·Q3·Q4는 전부 "42명을 어떻게 늘어놓고 볼 것인가"의 문제입니다. 화면을 세 개로 나누면 관리자가 어디서 뭘 볼 수 있는지 기억해야 하고, 매번 이동해야 합니다.

→ **사원 목록 하나에 "보기 방식" 전환을 넣습니다.** 같은 데이터를 정렬·필터·묶음만 바꿔서 보여주는 방식이며, 50명 규모에서는 이게 대시보드를 여러 개 만드는 것보다 훨씬 잘 작동합니다.

**규모 때문에 처음부터 배제한 것**

| 일반적인 HR 대시보드 기능 | 우리 가능 여부 |
|---|---|
| 부서별 비교 | ❌ 부서당 5~10명 (F-12 제외 결정) |
| 시계열 변화 추적 | ⚠️ D-10 변경으로 재응시가 가능해져 **원리상으로는 가능해짐.** 다만 30일 간격이라 의미 있는 시계열이 쌓이려면 오래 걸리고, 회차별 응시자가 들쭉날쭉해 전체 추세로는 못 읽음. **1차 범위에서는 계속 제외**하고, 데이터가 쌓이면 재검토 |
| 척도 간 상관분석 | ❌ 50명이면 매우 불안정 |
| 전체 분포 보기 | ✅ |
| 개인을 전체와 비교 | ✅ n≥30일 때 |
| 유형별 묶어보기 | ⚠️ 8칸에 50명이면 칸당 5~6명. **"통계"가 아니라 "훑어보기"로만 쓸 것** |

**사용 빈도 전제** — 관리자는 ① 응시가 어느 정도 진행됐을 때 한 번, ② 전원 응시가 끝난 뒤 한 번, 이렇게 봅니다. 상시 모니터링용이 아닙니다.

→ 대시보드를 **응시 중 / 응시 완료 두 국면**으로 나눠 설계합니다. 응시 중에는 "얼마나 왔나", 완료 후에는 "무엇이 보이나"가 중심입니다.

```
│    필요                  │                          │
└──────────────────────────┴──────────────────────────┘
```

**평균만 보여주지 않고 "퍼짐 정도"를 같이 보여주는 이유 (Q1)**

평균만 보면 안 보이는 게 있습니다. 예를 들어 `HA 평균 41`과 `ST 평균 47`은 숫자가 비슷하지만, HA는 다들 비슷하게 답했고(퍼짐이 좁음) ST는 사람마다 극과 극일 수 있습니다(퍼짐이 넓음). **관리자가 알고 싶은 건 "우리 회사가 어떤 성향이냐"인데, 그 답은 평균이 아니라 "어디가 모여 있고 어디가 갈리느냐"에 있습니다.**

| 표시 | 읽는 법 |
|---|---|
| 막대 위치 | 평균이 어디쯤인지 |
| 막대 길이(퍼짐) | 짧으면 "다들 비슷", 길면 "사람마다 다름" |
| `◀좁` / `◀넓` 표시 | 가장 의견이 모인 척도 / 가장 갈리는 척도를 자동으로 짚어줌 |

**국면별 대시보드** — 관리자는 ① 응시 중, ② 응시 완료 후 두 시점에 봅니다.

| 국면 | 상단에 오는 것 | 하단 |
|---|---|---|
| 응시 진행 중 (완료 < 전체) | 진행 현황 카드 4종 | 성향 분포는 "n=28, 참고용" 흐리게 |
| 응시 완료 후 | 성향 분포 | 진행 현황은 접어둠 |

**"검사 품질" 카드는 일반 설문 도구에 없는 우리 고유 기능입니다.** 자체 제작 검사라 신뢰도가 미지수인데, 이 카드가 없으면 문제를 영영 모릅니다. 응답이 30건 이상 쌓이면 활성화됩니다.

#### 보기 2. 사내 분포에서의 위치 — Q3

> ⚠️ **이 화면은 "판정"이 아니라 "정렬"입니다.**
>
> 초안에서는 시스템이 "눈에 띄는 사람"을 골라내는 방식으로 설계했으나, **그 선별 기준 중 일부가 학술적 근거 없이 만들어낸 규칙**이었습니다. 특히 "7척도가 모두 중간이면 불성실 응답 신호"는 **어떤 문헌에도 없는 추측**이며, 실제로는 균형 잡힌 응답일 수 있는 사람을 근거 없이 걸러내는 문제가 있어 **삭제했습니다.**
>
> 우리 시스템이 근거를 갖고 말할 수 있는 것은 두 가지뿐입니다.
> ① **응답 품질** — 응답시간·역채점 일치도. 연구로 검증된 지표 (`00` §2.3)
> ② **분포상 위치** — 사내 응답자 중 이 사람 점수가 어디쯤인지. 단순 계산이며 해석을 포함하지 않음
>
> 그 외의 "이 사람은 특이하다" 류 판정은 넣지 않습니다.

> **이름 붙은 정렬 리스트를 유지합니다 (확정).** 기술검토서(참고 자료)의 "사내 순위 매기기 금지" 문구를 이유로 한때 이 리스트를 뺐으나, 이건 **관리자 전용 · 감사 로그 기록 · 사내 분석 목적**이라는 이 화면의 전제와 맞지 않는 과도한 적용이었습니다. 관리자가 "누가 어느 척도에서 두드러지는지" 보는 건 §4.0에서 정의한 Q3에 대한 정당한 답이며, 사용자가 명시적으로 원하는 기능입니다. **참고 문서의 지침보다 실제 결정이 우선합니다.**

```

│                                                          │

│              20  40  60  80  100                         │
│              평균 54.2 · 표준편차 12.8                    │
│                                                          │
│  ─────────────────────────────────────────────────       │
```

| **개인 결과 화면(`/me`)에는 절대 표시하지 않음** | §17 라벨링 금지 취지("우열 없음")와 순위 비교가 부딪힘. 사용자 확정 |
| 응시 완료 **30명 이상**일 때만 이 항목 노출 | 30명 미만이면 통계적으로 불안정 (D-24) |
| **스냅샷이 아니라 항상 최신값으로 계산** | 개인 결과(`/me`)는 §2.6대로 영구 고정이지만, 이 값은 관리자가 조회하는 시점마다 그때까지의 전체 데이터로 재계산. "먼저 본 사람은 갱신 안 됨" 문제 자체가 없음 — 애초에 개인에게 보여준 적이 없으므로 |
| "참고용" 표기 상시 노출 | n이 30~50 구간에서는 여전히 표본이 작음 |

**감사 로그 기록 시점**: 페이지 진입 시 서버 컴포넌트에서 기록합니다. 클라이언트에서 보내면 우회 가능합니다.

```ts
// app/(admin)/admin/employees/[id]/page.tsx
export default async function Page({ params }) {
  const admin = await requireAdmin()          // 권한 검증
  await recordAudit({                          // 감사 로그 — 조회 전에 기록
    actorId: admin.id,
    action: 'VIEW_INDIVIDUAL_RESULT',
    targetEmployeeId: params.id,
  })
  const result = await getResult(params.id)
  return <IndividualResult data={result} />
}
```

**② 두 축 비교 (산점도) — 신규 (F-35)**

축 두 개를 골라 사람을 좌표에 흩뿌립니다. "자극추구는 높은데 위험회피도 높은 사람"처럼 **두 성향의 조합을 눈으로 찾는** 용도입니다.

```
    위험회피 ↑
      100 │        ·
          │    ·  ·   ·
       50 │  ·  ·· ·  ·
          │ ·  ·   ·
        0 └──────────────→ 자극추구
          0     50    100
   점에 마우스를 올리면 이름 표시. 클릭하면 개인 상세로 이동
```

| 규칙 | 이유 |
|---|---|
| 상관계수·회귀선 **표시 안 함** | n≤50에서 상관 추정은 매우 불안정. `00` §6에서 "척도 간 상관분석" 제외 확정 |
| "탐색용, 통계 아님" 안내 상시 | 점 분포에서 없는 패턴을 읽어내는 것 방지 |
| n<30이면 비활성 | 다른 분포 표시와 동일 기준 |

> 💡 **왜 상관분석은 빼고 산점도는 넣는가**: 상관계수는 "두 축이 관련 있다"는 **추론**이라 표본이 작으면 틀립니다. 산점도는 "이 사람들이 여기 있다"는 **사실의 나열**이라 표본과 무관하게 정확합니다. 판정하지 않고 보여주기만 한다는 §4.0 원칙과 일치합니다.

**③ 축별 평균 순위 — 신규 (F-36)**

7개 축을 사내 평균이 높은 순으로 정렬해 한눈에 보여줍니다. "우리 회사는 연대감이 높고 위험회피가 낮은 편"을 즉시 파악하는 용도입니다. 표준편차를 함께 표시해 **평균이 비슷해도 갈리는 정도가 다른 축**을 구분할 수 있게 합니다.

**④ 응시 진행 추이 — 신규 (F-37), 대시보드에 배치**

날짜별 누적 응시 완료 인원을 꺾은선으로 표시합니다. 순수 운영 지표라 표본 크기 문제가 없고, "이번 주에 몇 명 늘었나"를 바로 알 수 있습니다. 전원 응시가 끝나면 자동으로 접힙니다.

**⑤ 응답 품질 요약 — 신규 (F-38), 대시보드에 배치**

전체 중 검토가 필요한 응답이 몇 건인지, 어떤 사유인지(응답시간 미달 / 반대 문항 불일치)를 카드 하나로 요약합니다. 지금은 개인 상세에 들어가야만 볼 수 있어 문제를 놓치기 쉽습니다.

**⑥ 개인 결과에 사내 평균 겹쳐 보기 — 신규 (F-39), 개인 상세에 배치**

개인 상세의 레이더 차트에 **사내 평균을 점선으로 겹쳐** 그립니다. 숫자로 "상위 34%"라고 보는 것보다 어느 축이 튀는지가 훨씬 빨리 읽힙니다.

> ⚠️ `00` §6의 제외 목록에 "레이더 오버레이"가 있으나 그건 **부서 평균끼리 겹치는 것**을 말합니다(부서당 5~10명이라 표본 부족). **개인 vs 전체 평균**은 전체 n이 기준을 넘으면 성립하므로 다른 사안입니다. 동일하게 n≥30에서만 표시합니다.
>
> 개인 화면(`/me`)에는 넣지 않습니다 — D-09(사내 상대위치는 개인에게 표시하지 않음)에 걸립니다.

**공통 규칙**: 모든 분포·평균 표시는 `n < 30`이면 비활성화하고 안내만 띄웁니다. 표본이 작다는 걸 관리자가 잊으면 없는 패턴을 읽어냅니다.

### 4.5.1 관리자 로그인 화면 — 신규 (F-40, D-05 변경)

```

│  관리자 로그인               │
│                             │
│  아이디    [___________]    │
│  비밀번호  [___________]    │
```

| 항목 | 처리 |
|---|---|
| 비밀번호 저장 | **bcrypt 해시.** 평문·단순 해시 금지 |
| 초기 비밀번호 | seed로 생성, 환경변수 `ADMIN_INITIAL_PASSWORD`로 주입 |
| **최초 로그인** | `passwordChangedAt`이 비어 있으면 **변경 화면으로 강제 이동.** 바꾸기 전에는 다른 관리자 화면 접근 불가 |
| 실패 제한 | **15분 내 5회** (사원은 10회). 권한이 크므로 더 좁게 |
| 오류 메시지 | "아이디 또는 비밀번호가 올바르지 않습니다" — 어느 쪽이 틀렸는지 알려주지 않음 |
| 사원 로그인과의 관계 | 완전히 별도 경로. 사원 화면(`/login`)에서는 관리자 로그인이 되지 않음 |

**관리자도 설문에 응시할 수 있습니다.** `Employee` 레코드를 공유하므로 관리자 세션으로 `/test`·`/me`에 접근 가능합니다. 대표가 본인 결과를 보려면 별도 계정을 만들 필요가 없습니다.

**비밀번호 변경 화면(`/admin/password`)**은 현재 비밀번호를 함께 요구합니다. 세션만 탈취해도 비밀번호를 바꿔버릴 수 있으면 계정을 되찾을 수 없게 됩니다.

### 4.6 감사 로그 및 사원 현황 — 신규 (F-27, F-28)

| 규칙 | 이유 |
|---|---|
| 저장 전 반드시 `normalizePhone()` 통과 | 관리자가 손으로 입력한 값이 로그인 시 정규화되는 값과 어긋나면 그 사원은 영원히 로그인 못 함. **로그인과 이 화면, 두 진입점 모두 예외 없음** |
| (이름, 전화번호) 중복이면 에러 표시 | 유령 계정 방지 |

#### 구성원 데이터 삭제 (F-33) — ✅ 확정

**용도**: 퇴사자 정리, 오타로 생긴 유령 계정 정리. D-25가 A안(자율 등록)이라 오타 계정이 생길 수 있으므로 정리 수단이 반드시 필요합니다.

| 항목 | 내용 |
|---|---|
| 위치 | 구성원 목록의 행 메뉴 + 개인 결과 상세 화면. 양쪽 모두 낮은 강조도의 보조 동작 |
| 확인 절차 | **대상자 이름을 직접 입력해야 실행.** 단순 "확인" 버튼으로는 부족 — 되돌릴 수 없는 동작이라 오클릭 방지가 필요 |
| 삭제 대상 | `Employee` + 연결된 `AuthSession` · `TestSession` · `Response` · `Result` · `QualityFlag` 전부 (Prisma `onDelete: Cascade`로 자동 처리) |
| **삭제하지 않는 것** | **`AuditLog`.** 아래 참조 |
| 감사 로그 | `action: 'DELETE_EMPLOYEE'` |

> ⚠️ **감사 로그에 이름을 함께 저장해야 합니다 — 안 하면 기록이 무의미해집니다.**
>
> `AuditLog.targetEmployeeId`는 FK 제약이 없는 단순 문자열이라 사원이 삭제돼도 로그 행은 남습니다. **그런데 그 ID로 조회할 대상이 사라졌으므로 "누구를 지웠는지" 알 수 없게 됩니다.** 삭제 기록만 남고 대상을 모르면 책임 추적이 성립하지 않습니다.
>
> → `AuditLog`에 `targetName` 컬럼을 추가하고, **삭제 시점의 이름을 스냅샷으로 저장**합니다. 다른 액션에서는 비워둬도 되고 `DELETE_EMPLOYEE`에서만 채웁니다.

```ts
export const AUDIT_ACTIONS = {
  VIEW_INDIVIDUAL_RESULT: 'VIEW_INDIVIDUAL_RESULT',
  ADD_EMPLOYEE: 'ADD_EMPLOYEE',
  RESET_ASSESSMENT: 'RESET_ASSESSMENT',
  EXPORT_CSV: 'EXPORT_CSV',
  DELETE_EMPLOYEE: 'DELETE_EMPLOYEE',   // 신규
} as const
```

**응시 초기화(F-30)와의 차이** — 초기화는 응답·결과만 지우고 계정을 남겨 재응시 가능하게 하는 것이고, 삭제는 계정 자체를 없애는 것입니다. 화면에서 두 동작이 나란히 보이면 혼동되므로 **문구를 명확히 구분**합니다("응시 기록 초기화" / "구성원 삭제").

**관리자 자신은 삭제할 수 없습니다.** 마지막 관리자를 지우면 아무도 관리자 화면에 들어갈 수 없게 됩니다. 서버에서 `role === 'ADMIN'`인 대상은 삭제를 거부합니다.

**이 화면 자체를 여는 행위는 감사 로그에 남기지 않습니다.** 로그를 보는 것까지 로그로 남기면 재귀적으로 늘어나기만 하고 실익이 없다는 판단입니다.

**API**

```
GET  /api/admin/audit              감사 로그 목록 (필터: 관리자, 기간)
POST /api/admin/employees          사원 수동 추가
```

`recordAudit()`은 §4.4에서 이미 정의한 함수를 그대로 씁니다. `AUDIT_ACTIONS`에 `ADD_EMPLOYEE`만 추가합니다.

```ts
export const AUDIT_ACTIONS = {
  VIEW_INDIVIDUAL_RESULT: 'VIEW_INDIVIDUAL_RESULT',
  ADD_EMPLOYEE: 'ADD_EMPLOYEE',   // 신규
} as const
```

## 6. 구현 구조

### 6.1 컴포넌트 트리 (응시 화면)

```
<TestSectionPage>              서버 컴포넌트 — 섹션 문항 로드
  └ <SectionForm>              클라이언트 — 응답 상태 보유
      ├ <ProgressHeader>       바 + 섹션 N/7
      ├ <ItemList>
      │   └ <ItemRow>          ×N
      │       ├ <ItemLegend>   sr-only 위치 안내 + 문항문
      │       └ <LikertGroup>  네이티브 radio ×5
      └ <SectionFooter>        미응답 경고 + 다음 버튼
```

**상태를 `SectionForm` 한 곳에만 둡니다.** `ItemRow`는 값과 콜백만 받는 표시 전용입니다. 이렇게 해야 자동저장·포커스 이동·미응답 검증이 한 군데서 처리됩니다.

### 6.2 포커스/디밍 로직

```ts
// SectionForm 내부
const [answers, setAnswers] = useState<Map<string, number>>(new Map())

// 활성 문항 = 아직 답 안 한 것 중 가장 앞
const activeIndex = items.findIndex(it => !answers.has(it.id))

function handleAnswer(itemId: string, value: number) {
  setAnswers(prev => new Map(prev).set(itemId, value))
  persistLocal(itemId, value, elapsedMs())
  // activeIndex가 자동으로 다음으로 밀림 → 다음 문항이 활성화
}
```

**주의**: 답을 고치면 `activeIndex`가 그 문항으로 되돌아갑니다. 그러면 스크롤이 위로 튀어서 어지럽습니다.

```ts
// 수정: "가장 앞의 미응답" 대신 "방문한 적 없는 것 중 가장 앞"
const [visited, setVisited] = useState<Set<string>>(new Set())
const activeIndex = items.findIndex(it => !visited.has(it.id))
```

이런 게 벤치마크를 눈으로만 봐서는 안 보이는 부분입니다.

### 6.3 API

```
POST /api/sessions                     세션 시작 (또는 기존 세션 반환)
GET  /api/sessions/current             진행 상황 조회
PUT  /api/sessions/[id]/sections/[n]   섹션 응답 저장 (배치)
POST /api/sessions/[id]/submit         제출 → 채점 → 결과 생성

GET  /api/me/result                    본인 결과 (스냅샷)

GET  /api/admin/summary                요약 카드
GET  /api/admin/employees              목록 (페이지네이션)
GET  /api/admin/employees/[id]         개인 상세 → 감사 로그
GET  /api/admin/stats/[scale]          척도별 분포
GET  /api/admin/export                 CSV → 감사 로그
```

**권한 검증은 모든 핸들러 첫 줄에서 합니다.** 프론트에서 메뉴를 숨기는 건 보안이 아닙니다.

```ts
// /api/me/result
const session = await requireAuth()
const result = await db.result.findFirst({
  where: { session: { employeeId: session.employeeId } }  // ← 본인 것만
})
```

`/api/results/[id]` 형태로 만들지 않는 게 핵심입니다. **ID를 받지 않으면 남의 것을 요청할 방법이 없습니다.** 요청 파라미터를 검증하는 것보다 파라미터를 없애는 게 안전합니다.

> 다만 이건 인증이 제대로 될 때의 이야기입니다. 현재 이름+전화번호 방식에서는 **로그인 자체가 사칭 가능**하므로 이 방어는 절반만 작동합니다. (D-05 재검토 시 해결)

### 6.4 저장 데이터 흐름

```
클라이언트                      서버                     DB
    │
  응답 클릭
    │─ localStorage 저장
    │
  섹션 완료
    │──── PUT /sections/3 ────→ 권한 검증
    │      [{itemId, value,      ↓
    │        elapsedMs}, ...]   버전 확인 (pin된 것과 일치?)
    │                            ↓
    │                          upsert ──────────→ responses
    │←──── 200 ────────────────
  다음 섹션

  마지막 섹션 후
    │──── POST /submit ───────→ 완결성 검증
    │                            ↓
    │                          채점 (순수함수)
    │                            ↓
    │                          품질 지표 계산
    │                            ↓
    │                          스냅샷 생성 ──────→ results
    │                                              quality_flags
    │←──── 결과 ID ────────────
  /me로 이동
```

## 7. 화면별 우선 구현 순서

| 순서 | 화면 | 이유 |
|---|---|---|
| 1 | 로그인 | 나머지 전부의 전제 |
| 2 | 응시 (섹션 1개만) | 가장 어려운 상호작용. 먼저 검증 |
| 3 | 채점 엔진 + 테스트 | 화면 없이 테스트만으로 검증 가능 |
| 4 | 결과 화면 | 채점이 맞는지 눈으로 확인하는 수단 |
| 5 | 응시 전체 (7섹션 + 저장) | 1개가 되면 나머지는 반복 |
| 6 | 관리자 목록 + 개인 상세 | |
| 7 | 요약 대시보드 | 데이터가 쌓여야 의미 있음 |
| 8 | 품질 지표 · CSV | |

**2번을 3번보다 먼저 두는 이유** — 응시 화면의 포커스/디밍/자동저장이 이 프로젝트에서 기술적으로 가장 까다롭습니다. 여기서 막히면 설계를 바꿔야 하는데, 나중에 발견하면 이미 만든 게 많아집니다.
